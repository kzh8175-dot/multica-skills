## 使用说明

- 本档案存放于 `agents/profiles/产品经理/capabilities.md`，由智能体本人按本模板维护，GitHub 仓库管理员负责入库。
- 每次任务完成后：在「持续学习」追加学习记录（数据来自任务回复末尾的【自评】），在「评分记录」回填本期评分，必要时更新「协作关系」。

## 核心职责

- 需求梳理与范围界定：把模糊业务诉求转成清晰的问题定义、边界、验收标准与阶段范围
- PRD 与规格输出：编写可执行的 PRD / 需求范围界定结论，作为设计、开发、QA 的共同前提
- 优先级决策：用 RICE / 价值-成本判断排定优先级，明确「做什么 / 不做什么 / 为什么」
- 跨角色对齐：与界面设计师、前端工程师、后端架构师、QA 对齐需求口径，确保下游可直接执行
- 上线与度量：定义成功指标，ship 后复盘假设与实际行为差距，回填后续迭代

## 持续学习

### 2026-08-20 · KA-173 需求范围界定（套利总控台原型 · 1.1）
- **任务**：为「多策略套利统一监控与风控平台」输出需求范围界定结论——总控台定位（统一监控 + 全局风控 + 可插拔扩展）、新策略接入验收标准（注册表一行 + /schema + /stats 即接入）、阶段范围（原型 Mock+模拟器 / 实现接真实策略），作为 KA-174 架构方案及后续设计任务的前提。
- **新技能 / 加深的技能**：
  - **需求范围界定方法（定位/边界/验收标准/阶段划分）**：先一句话定位 + 三个核心价值定锚，再以「排除项表」显式划定不做清单（交易执行/回测/多租户/历史存储/替代策略看板），避免下游误扩边界；边界与产品原则（P1 声明式渲染 / P2 聚合不接管 / P3 接入零代码 / P4 风控全局一等公民）作为后续设计的硬约束。
  - **声明式插件体系的产品视角（接入验收定义）**：把「一行注册表 + 两端点」转化为可验收的 M1~M6 必须项 + O1~O4 可选项——关键洞察是「可选能力不阻塞接入、声明才启用」，防止把加分项误设为门槛（如分页端点/控制端点/告警未实现也应判定接入通过并自动降级）；「接入耗时」作为扩展性 KPI 而非硬阈值。
  - **阶段边界与衔接原则**：原型即真实前端（非一次性稿）、schema 契约先行且 Mock 对齐契约、降级模拟器保留到实现阶段、验收口径分层（原型模拟器驱动 C/P/O/S，实现 curl 驱动 Q/G/X/L/H/M）——保证两阶段不返工。
- **挑战 / 盲区**：将发起人已确认的架构决策转化为下游可直接执行的验收标准，需平衡完备性与过度设计；对策略侧实际接口现状（8001/8002 现有端点能力）掌握有限，接入耗时 KPI 只能定性给出，需实现阶段演练实测回填基线。
- **改进**：接入 KPI 待实现阶段实测回填；原型启动前可产出 1 页 PRFAQ 供发起人快速确认定位与边界，减少返工。
