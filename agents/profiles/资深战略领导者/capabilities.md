### 2026-08-17 · KA-45 补记试点 P0 预算上限（budget.ceiling + tier）的确认与审批
- **任务**：所有者要求「与资深战略领导者确认，和审批」。对财务规划与分析分析师完成的 14 个 P0 子项 + 锚点 KA-40 的 `budget.ceiling` / `tier` 补标做核验并给出批准结论。
- **新技能 / 加深的技能**：
  - 审批前独立核验 metadata 落地（`multica issue metadata list` 逐项核对），不轻信执行者自评——本次逐项比对 14 个 issue，确认 ceiling/tier/lane/entry 与声明一致。
  - SOP §3.1「任一命中即 L」的子项继承判定：结算/评分账目核心（涉核心）+ 跨部门依赖 → 锚点 KA-40 为 L，其子项统一 L 级在结构上一致；单项直接成本小（¥10–100）不改变归属。
  - 锚点—子项双层预算核算：子项 ceiling 合计 ¥500 + 历史基线 KA-16 ¥157 = ¥657 < 锚点 ¥1000，落在 P0 批准口径 ¥554 + 质量缓冲内；审批关注「汇总是否越锚点」而非单项大小。
  - 超支冻结门禁应锚定**项目级**（锚点 ceiling）而非子项级：微小子项（¥10–20）若按 L 5% 阈值单点触发会虚报冻结；variance 按锚点汇总结算，子项只做归因。
- **挑战 / 盲区**：
  - 打标项（KA-17/18/19/20/43/44）审批时已转 `done`，需区分「历史基线用途」与「活跃用途」：done 项的 ceiling 留作超支率基线，不删。
  - 错峰 backlog 批（KA-21/23/26/28/29/30/31/32）有截止日（08-18~08-21）且尚未投入；其中 KA-23 与已完成 P0-1（KA-16）可能冗余——审批需附条件：截止前未投入则取消并移除 ceiling，避免对账误报。
  - 财务分析师明确「记账/打标不涉及资金支出审批」，审批边界需与 KA-45 描述一致：批准的是记账口径与预算上限，不是资金授权。
- **改进**：
  - 审批回复固定四段结构：**核验结论 → 批准范围 → 附条件 → 后续责任**，避免笼统通过。
  - 对账 autopilot 的阈值语义（子项 vs 锚点）需在 SOP §4 补充口径说明，防止微小项虚报冻结。

- **新技能 / 加深的技能**：
  - 通读 14 个 superpowers 技能（using-superpowers 启动总控 / brainstorming 设计门禁 / writing-plans / executing-plans、subagent-driven-development、dispatching-parallel-agents 执行三件套 / using-git-worktrees / TDD / systematic-debugging / verification-before-completion / 双向 code-review / finishing-a-development-branch / writing-skills），理解各自触发条件与铁律。
  - 关键判定：`executing-plans` 与 `subagent-driven-development` 属同一执行环节的两种模式——平台支持子代理时 SDD 优先，EXP 仅作无子代理/顺序执行时的回退。
  - 「按需精准」技能裁剪方法论：编码/技术类智能体装全链（设计→计划→隔离→TDD→调试→验证→审查→合入），管理/创意/市场类按职责装核心环节（BRA+WPL+VER 三件套，按需补 DBG/TDD/DPA），避免全员全量造成行为强塑过度。
  - 用数据驱动脚本生成双向映射并加断言校验（66/66 覆盖、14 技能均有安装者、无重名），交付前以「评论区全文 + 附件」双通道保证文档即达。
- **挑战 / 盲区**：
  - 异构智能体（编码 vs 内容 vs 客服 vs 财务）承接软件开发方法论的口径差异——提炼通用环节（证据验证、根因归因、设计先行）按职责映射而非生搬。
  - 名单内「UI设计师」与「UI 设计师」（一个空格之差）是两个不同智能体，需在映射中分别覆盖，防止误合并。
  - 本能力档案在仓库内多分支分散（KA-45 建档停留在 `agent/agent/93470ea7` 未合入 main），本次基于既有档案续写并合入 main。
- **改进**：
  - 后续可结合各技能实际导入/安装状态，为每个智能体标注安装优先级与试点批次（本任务已给出四批安装建议）。
  - 此类全量规划任务先以脚本生成+校验降低人工遗漏风险，再人工复核依据措辞。

### 2026-08-17 · KA-60 执行落地：导入 14 技能并安装到全部 66 智能体
- **任务**：按所有者要求「根据安装批次建议，现在就执行」，将 14 个 superpowers 技能逐个导入工作区、技能英文名改为中文名，并按映射安装到全部 66 个智能体。
- **新技能 / 加深的技能**：
  - 技能导入机制：`multica skill import --url https://github.com/obra/superpowers/tree/v6.3.0/skills/<name>` 可从 GitHub 仓库子目录直接导入技能（tree 目录形式），返回结构化信封（status/skill.id/files）。
  - 技能改名：`multica skill update <id> --name <中文名>` 可独立于内容修改工作区技能显示名（14 个已全部改为中文：超级技能引导/头脑风暴/编写实现计划/执行实现计划/子代理驱动开发/并行派发子代理/Git工作区隔离/测试驱动开发/系统性调试/完成前验证/请求代码审查/接收代码审查/开发分支收尾/编写技能）。
  - 技能绑定：`multica agent skills add <agent-id> --skill-ids <逗号分隔>` 为追加式（保留已有 persona+agent-skill-creator），返回的是该 agent 全部技能列表（数组），不能用 `.get` 解析——需按数组校验。
  - 批量执行方法论：数据驱动（agent 名单+映射）+ 先校验后执行 + 逐 agent 回读核验（66/66 无缺失，共 361 个安装项）；批次建议拆为 8/8/7/43 四批推进。
- **挑战 / 盲区**：
  - `multica agent skills add` 输出为技能列表数组而非 `{added:...}`，初版解析误判为失败——教训：先以单条命令确认响应形状，再批量。
  - 导入批量循环曾因单条挂起导致 2 分钟超时；改为逐条带进度输出+长超时后全部成功。
  - 改名只影响显示名，技能内容（SKILL.md）仍为英文、内部互相引用英文名；后续 `using-superpowers` 引导内容与中文技能名的映射一致性需在推广时关注。
- **改进**：
  - 大规模型 CLI 操作先小样本探测响应结构，再写批量校验脚本。
  - 交付时在回复中附「技能中文名 + 各批次安装计数」汇总，便于所有者核对。

### 2026-08-17 · 收口 SOP 试点 4 项（KA-38/39/40/45）
- **任务**：所有者要求完成 SOP 项目下 4 个 in_progress issue——Layer 2 落位（KA-38）、Layer 3 autopilot 治理复核（KA-39）、试点切轨（KA-40）、预算补标（KA-45）。核心是核验各岗位已完成的执行成果、补齐未收口点、置 done。
- **新技能 / 加深的技能**：
  - **「收口模式」**：执行内容已由委派 agent 完成并登记（KA-35），但 issue 停在 in_progress——收口 = 核验证据（KA-35 登记 / 评论 / metadata 三路）+ 补齐遗留点 + 关闭说明 + `status done --no-start`（防触发新 run）。
  - **引用块口径修正**：项目负责人 SOP 块「五维准入初判」实为轻量通道准入四维混入 S/M/L 判定；正确五维 = 直接成本/工时/部门依赖/对外/资金数据合规。修正 = 只改 agent instructions 一行并回读验证（引用块计数/persona/skills 不变）。
  - **autopilot 治理落地**：评审结论（需调整）→ 把护栏写进 autopilot description（冻结三守卫/解冻分支/去重冷却/豁免清单/工作日口径/建议制 + 所有者确认）、改派执行 agent（监控独立）、补 `issue-title-template "…{{date}}"`——全部可回滚。
  - **试点验收报告结构**：基础达标（一期完成 ✅ + 复盘待开 ⏳）/ 进阶口径（基线 vs 试点初步对比）/ 风险如实上报 / L 级门禁执行 / 后续。关键纪律：不假装复盘已开——创建复盘 issue（KA-64）作为基础达标最后门槛。
- **挑战 / 盲区**：
  - `multica issue comment add` 输出为「Comment added…」文本 + JSON 混合，直接 json.load 会解析失败并误以为失败 → 误触发重复评论；清理用 `multica issue comment delete <comment-id>`（仅接受 comment-id 单参，不接受 issue+comment 双参）。
  - `multica autopilot get` 返回嵌套 `{"autopilot":{...}}`，与 `autopilot list` 的扁平数组不同，脚本解析需按接口调整。
  - 治理调整（改 autopilot 描述/改派执行 agent）是生产自动化行为变更，即使可回滚也须在每个关闭评论中透明记录，供所有者复核回滚。
- **改进**：
  - 评论提交用 `grep -E 'Comment added|error'` 确认而非 json 解析，杜绝重复提交。
  - 跨 issue 收口前先统一拉齐 KA-35 登记 / 评论 / metadata 三路证据，再决定各 issue 缺什么，避免漏收口点。
